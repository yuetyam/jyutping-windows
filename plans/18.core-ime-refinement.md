# Refined CoreIME Port Roadmap

This roadmap updates the Windows input engine to match the current desktop
behavior of the Swift `CoreIME` package. It replaces the older bundled-engine
database contract and ports the refined segmentation, lookup, ranking,
supplementary candidate, and candidate-conversion pipeline.

The Windows `InputMemory` implementation is not part of this port. Its database
schema, hashes, search behavior, ranking, learning, forgetting, and migration
policy should remain unchanged.

## Goals

- Make normal 26-key Jyutping suggestions match the refined Swift engine.
- Adopt the generated desktop CoreIME schema and serial key-code encoding.
- Port the refined full-key segmenters and all desktop reverse-lookup modes.
- Port plain-text, emoji, symbol, and character-standard behavior.
- Separate engine-level `Lexicon` values from display-ready `Candidate` values.
- Centralize candidate-source ordering and deduplication in a Converter-style
  pipeline.
- Keep TSF-specific composition and candidate-window code outside CoreIME.
- Keep Windows input memory behavior stable across the cutover.
- Use applicable Swift CoreIME examples as read-only behavior references during
  manual verification.

## Non-Goals

- Do not port `InputMethod/Models/InputMemory.swift`,
  `Keyboard/SharedModels/InputMemory.swift`, or any Swift memory migration.
- Do not change `Jyutping/InputMemory.h` or `Jyutping/InputMemory.cpp` unless a
  later, separately approved memory roadmap requires it.
- Do not change `%LOCALAPPDATA%\Jyutping\memory.sqlite3` or the `core_memory`
  schema.
- Do not replace the memory `HashCode` encoding with CoreIME serial key codes.
- Do not port `Combo`, `NineKeySegmenter`, `NineKeyEngine`,
  `PinyinNineKeySegmenter`, or any `*_9key` query.
- Do not port iOS ambiguous-key input or `AmbiguousInputEvent`; Windows receives
  deterministic physical 26-key QWERTY key events.
- Do not port Swift concurrency mechanics. The current TSF engine is
  synchronous; `Task.isCancelled` has no direct Windows equivalent.
- Do not port the Swift CoreIME tests or benchmarks.
- Do not add a Windows CoreIME test project, test harness, benchmark project,
  benchmark mode, or benchmark deliverable. Swift test and benchmark sources
  may be inspected only to understand expected engine behavior.
- Do not add an emoji browser, system text-replacement source, custom/OpenCC
  provider, or new settings UI. Core APIs may support those sources, but the
  Windows adapter may pass an empty source until a separate UI roadmap exists.
- Do not rewrite TSF composition, candidate navigation, punctuation candidate
  mode, or the candidate window except where the new typed candidate boundary
  requires a narrow adapter change.

## Current Windows Baseline

The Windows code already contains earlier ports of much of CoreIME:

- `VirtualInputKey.*`, `ImeTypes.*`, `Segmenter.*`, and
  `PinyinSegmenter.*` provide typed keys, lexicons, and segmentation.
- `InputEngine*.cpp` contains normal suggestions and the four reverse-lookup
  paths.
- `ImeDatabase.*` owns the read-only bundled SQLite connection.
- `CharacterStandard.*` contains the current variant converters.
- `InputMemory.*` is a separate writable per-user database.
- `CompositionProcessorEngine.*` combines lookup, presentation, TSF state, and
  candidate caching.

The important gaps are:

- The old `ime.sqlite3` contains the legacy schema and must be atomically
  replaced by the refined database generated by `preparing`.
- Current SQL targets the older `core_lexicon`, `core_syllable_table`,
  `pinyin_syllable_table`, and `mark_table` names.
- Current lexicon, Pinyin, structure, symbol, and plain-text queries use older
  hash-only matching and omit the refined `complexity` or `char_count` guards.
- Current stroke lookup expects an obsolete `spell` column.
- `InputEngine` mixes bundled CoreIME lookup with Windows input-memory
  orchestration.
- Candidate dispatch exists as private merging code in `InputEngine.cpp`, while
  character conversion and comment creation happen later in
  `CompositionProcessorEngine.cpp`.
- The lack of a native CoreIME test or benchmark target is intentional for this
  roadmap.

## Target Ownership

Keep four responsibilities distinct:

```text
Windows key event
    -> VirtualInputKey / BasicInputEvent
    -> desktop CoreIME engine
         -> segmentation
         -> bundled database lookup
         -> Lexicon results
    -> Windows source orchestration
         -> existing InputMemory suggestions
         -> plain text and symbols
         -> Converter dispatch
         -> Candidate results
    -> TSF composition and candidate presenter
```

The implementation may keep the existing filenames, but the ownership boundary
must be explicit:

- The desktop CoreIME layer owns the read-only bundled database, segmenters,
  normal lookup, reverse lookup, supplementary queries, and character
  conversion. It must not depend on TSF or `InputMemory`.
- The Windows `InputEngine` facade owns or coordinates the unchanged
  `InputMemory`, gathers candidate sources, and forwards memory commands.
- `Candidate` retains its source `Lexicon`, so selecting a converted display
  candidate can still learn or forget the original Cantonese lexicon.
- `CCompositionProcessorEngine` owns input buffers, settings, TSF composition,
  and presentation lifetime, not lookup/ranking rules.

If a separate `CoreImeEngine` class is introduced to enforce this boundary,
move existing pure lookup code rather than duplicating it. Keep the public
Windows `InputEngine` facade so TSF call sites can migrate incrementally.

## Database Contract

The first active CoreIME cutover must update the database artifact and every
dependent query together. Do not point the old SQL at the regenerated
`ime.sqlite3`.

Required old-to-new mappings include:

| Older Windows contract | Refined desktop contract |
| --- | --- |
| `core_lexicon` | `lexicon_core` |
| `core_syllable_table` | `syllable_core_table` |
| `pinyin_syllable_table` | `syllable_pinyin_table` |
| `mark_table(mark, spell)` | `plain_text_table(input, word, letter_count, spell)` |
| lexicon `spell = HashCode(text)` | `spell = conjoined serial VirtualInputKey code` |
| anchors without a count guard | `anchors` plus `char_count` |
| spell without a count guard | `spell` plus `complexity` |
| stroke `spell` query | stroke `code` plus `complex`, or `stroke` pattern query |

The CoreIME database encoding and input-memory encoding are deliberately
different:

- CoreIME bundled tables use the serial/radix encoding generated by
  `preparing` and represented by `VirtualInputKey` combined codes.
- CoreIME `complexity` and shape `complex` values are signed 64-bit integers.
  Decimal complexity calculations use wrapping 64-bit arithmetic and may
  therefore produce negative values, matching Swift `Int` behavior.
- Input memory continues to use `HashCode` for its `shortcut` and `spell`
  columns.

Name query helpers so this difference remains visible. A broad mechanical
replacement of `HashCode` is forbidden because it would corrupt memory lookup
compatibility.

## Risks

- The old and new databases encode spell fields differently. A partial cutover
  can compile successfully while returning empty or incorrect candidates.
- `HashCode` remains correct for InputMemory but is wrong for the refined
  bundled CoreIME schema. Review every call by ownership, not by name alone.
- Omitting `complexity` or `char_count` can turn serial-code collisions into
  plausible but invalid candidates.
- Re-preparing SQLite statements inside prefix/slice loops can cause visible
  typing latency. Reuse statements within one request without sharing mutable
  statement state unsafely.
- Candidate conversion can lose the source lexicon and break learning if the
  display string becomes the selection identity.
- Extracting CoreIME and switching schema simultaneously is a large blast
  radius. Prepare the complete replacement path first, then perform one
  controlled runtime cutover followed immediately by focused runtime checks.
- Swift string counts and Windows UTF-16 code-unit counts are not always the
  same. Use semantic key/syllable complexity from the schema rather than
  inferring it from display-string length.
- Compile success does not validate TSF input counts, pre-edit marks, candidate
  lifetime, or memory behavior. Runtime confirmation remains mandatory.
