# Language-Bar Settings Menu Appearance Roadmap

This roadmap covers the settings menu opened by right-clicking the `Input Mode`
language-bar button. The direct popup should use the same visual language as the
candidate window: Windows-aware light and dark colors, translucent composition
where it is reliable, rounded corners, DirectWrite text with appropriate font
fallback, and DPI-correct layout.

The work is an appearance and presentation refactor. Existing commands,
localized labels, ordering, persisted values, candidate refresh behavior, and
the left-click input-mode toggle remain unchanged.

## Success Criteria

The refined direct popup must:

- open reliably from the existing `TF_LBI_CLK_RIGHT` path;
- preserve every current menu item, submenu, command ID, radio state, disabled
  state, and visible order;
- match the candidate window's theme, highlight, translucency, and corner
  treatment without inheriting candidate-specific sizing;
- use the Windows menu font metrics at the popup monitor's DPI, with a
  project-controlled fallback list for localized CJK and symbol text;
- support mouse and keyboard use, cascading submenus, cancellation, light
  dismissal, multiple monitors, and work-area clamping;
- expose menu and menu-item semantics to accessibility clients;
- avoid changing the foreground application, document focus, or TSF context
  after the popup closes; and
- fail cleanly without leaking windows, focus, capture, or timers if custom
  presentation cannot be initialized.

The TSF-hosted `ITfMenu` surface remains native and host-rendered. It must share
the same menu description and command IDs, but visual parity is not a contract
because the TSF host owns that surface.

## Scope Boundaries

In scope:

- the direct right-click settings popup in `CLangBarItemButton`;
- deriving the custom direct popup and `ITfMenu` compatibility surface from one
  semantic menu description;
- reusable window-appearance and DirectWrite helpers needed by both the
  candidate window and the new popup;
- popup rendering, input tracking, accessibility, DPI, theme, and degraded
  rendering behavior; and
- all project-file entries and lifecycle registration required by new C++
  files or window classes.

Out of scope:

- changing registry names, value ranges, defaults, or persistence behavior;
- adding, removing, relabeling, or reordering settings;
- changing candidate-window font-size settings or candidate layout;
- changing the `COptionsView` command set or its keyboard shortcut;
- enabling the disabled version/footer item currently named
  `IDS_MENU_MORE_SETTINGS` internally;
- changing the left-click `InputMethodMode` toggle or preserved keys;
- creating a full settings application; and
- installer or packaging changes beyond building the existing targets.

## Current Contract

`Jyutping/LanguageBar.cpp` currently owns three related responsibilities:

- `ShowSettingsMenu` creates the working direct `HMENU` popup with
  `CreatePopupMenu`, `AppendMenuW`, `CheckMenuRadioItem`, and `TrackPopupMenu`;
- `InitMenu` separately recreates the same hierarchy with `ITfMenu`; and
- `OnMenuSelect` dispatches stable command IDs through
  `ILangBarItemButtonSettingsMenuHandler`.

The direct popup is the runtime-proven right-click surface. An earlier
`ITfMenu`-only implementation compiled but did not appear in the tested shell,
so this roadmap must not make right-click behavior depend on `InitMenu`.

The current top-level order is a compatibility contract:

1. `IDS_MENU_CANDIDATE_FONT_SIZE`
2. `IDS_MENU_CANDIDATE_NUMBER_FONT_SIZE`
3. `IDS_MENU_CANDIDATE_COMMENT_FONT_SIZE`
4. `IDS_MENU_CANDIDATE_PAGE_SIZE`
5. `IDS_MENU_PUNCTUATION_FORM`
6. `IDS_MENU_CHARACTER_FORM`
7. `IDS_MENU_CHARACTER_VARIANT`
8. separator
9. disabled `IDS_MENU_MORE_SETTINGS` version/footer text

The resource strings, rather than the English fallback text in
`LanguageBar.cpp`, define the visible copy. The active resource tables are:

- `Strings.en-US.rc2`;
- `Strings.zh-CN.rc2`;
- `Strings.zh-HK.rc2`;
- `Strings.zh-MO.rc2`;
- `Strings.zh-SG.rc2`; and
- `Strings.zh-TW.rc2`.

Relevant appearance code already exists, but is not yet a reusable menu layer:

- `CandidateWindow.cpp` owns the acrylic accent call, rounded-corner request,
  DirectWrite role-format construction, DPI refresh, and D2D/GDI paint paths.
- `OptionsView.cpp` demonstrates candidate-style row measurement and rendering,
  selection/highlight colors, separators, checkmarks, and a GDI fallback. It
  is an embedded flat options view, not a cascading popup-menu implementation.
- `Globals.cpp` owns theme colors and the candidate, number, and comment font
  fallback objects.
- `BaseWindow.*` supplies the repository's popup-window lifecycle, capture,
  timer, work-area, and message-dispatch foundations.

## Design Decisions

### Make the Custom Window the Only Direct Popup

Owner-drawing an `HMENU` can change item content, but it does not provide a
stable supported window surface for candidate-style composition and cascading
submenus. Implement a focused custom popup for `ShowSettingsMenu`. Once it is
runtime-verified, remove the direct `HMENU` construction and `TrackPopupMenu`
path rather than maintaining a second popup implementation.

Do not hook process-global menu windows, subclass undocumented menu classes, or
force dark mode through process-wide state. The IME DLL runs in client
processes, so global UI mutations have an unacceptable blast radius.

### Share Semantics, Not Menu-Host Details

Create one immutable menu snapshot containing item kind, command ID, localized
text, enabled state, radio-checked state, and child items. Render that snapshot
into:

- the custom popup used by the direct right-click path;
- the TSF-owned `ITfMenu` compatibility path.

`OnMenuSelect` remains the only command dispatcher. Renderers must not save
settings, manipulate TSF compartments, or refresh candidates directly.

### Reuse Appearance Primitives Conservatively

Extract only genuinely generic pieces from `CandidateWindow.cpp`, such as
accent application, corner preference, color conversion, and text-format
creation. Keep candidate pagination, shadows, scrollbars, row geometry, and
`COptionsView` behavior in their existing owners.

The extraction must not alter candidate-window pixels or lifecycle behavior.
Capture a light- and dark-theme candidate-window baseline before the refactor
and compare it after the shared helpers land.

### Treat Accessibility and High Contrast as Core Behavior

A custom popup replaces native menu behavior, including accessibility. The
custom path is not complete until it reports menu/menu-item roles, names,
enabled and checked states, selection/focus changes, and invoke actions through
UI Automation or a compatible MSAA provider.

When Windows high contrast is active, disable translucent composition and use
system colors for background, text, highlight, disabled text, separators, and
focus indication. Readability takes precedence over matching the candidate
window tint.

## Implementation Phases

### Phase 1: Record the Runtime Baseline

Before changing menu construction:

1. Capture the current direct popup in light and dark themes.
2. Record root/submenu placement, checked values, disabled footer text, mouse
   dismissal, Escape behavior, and the foreground/focus state before and after
   dismissal.
3. Confirm the current localized labels and exact top-level order in all six
   resource tables.
4. Confirm each command still applies through `OnMenuSelect`, persists through
   the existing settings store, and refreshes live candidate state where it
   does today.
5. Record whether the current shell exposes `InitMenu`; absence does not block
   the roadmap, but semantic construction must remain valid.

This baseline is the regression reference for later phases.

### Phase 2: Introduce a Shared Menu Snapshot

Add a focused internal model, for example `SettingsMenuModel.h/.cpp`, with:

- `Command`, `Submenu`, and `Separator` item kinds;
- the existing stable command ID;
- localized display text;
- enabled and radio-checked state; and
- owned child items for submenus.

Build one snapshot from `ILangBarItemButtonSettingsMenuHandler`. Preserve the
current ID ranges and numeric mappings for font sizes `11..24`, page sizes
`1..10`, punctuation form, character form, and character variant.

Introduce the shared semantic path before adding custom presentation:

1. Populate `ITfMenu` from the snapshot, translating item state into
   `TF_LBMENUF_SUBMENU`, `TF_LBMENUF_RADIOCHECKED`, `TF_LBMENUF_SEPARATOR`, and
   `TF_LBMENUF_GRAYED`.
2. Keep the existing `HMENU` code unchanged only until the custom popup is
   ready to replace it; do not refactor it into a reusable fallback renderer.
3. Add debug-time validation that command IDs are unique and command items do
   not overlap submenu or separator IDs.
4. Manually compare the `ITfMenu` projection with the Phase 1 contract before
   moving on.

This phase must be independently shippable and must not change appearance.

### Phase 3: Extract Shared Appearance and Typography Helpers

Add a small shared module, for example `WindowAppearance.h/.cpp`, and move only
the reusable behavior currently private to `CandidateWindow.cpp`:

- dynamic lookup and invocation of `SetWindowCompositionAttribute`;
- `COLORREF` plus alpha conversion for the accent gradient value;
- DWM corner-preference application;
- Windows-version/capability checks; and
- creation of a DirectWrite text format with an optional fallback object.

Return explicit success/failure from composition helpers. Both callers must be
able to paint an opaque background when acrylic is unavailable, transparency
effects are disabled, high contrast is active, DWM composition is unavailable,
or API lookup fails.

For menu typography:

1. Query `NONCLIENTMETRICS.lfMenuFont` with
   `SystemParametersInfoForDpi(SPI_GETNONCLIENTMETRICS, ...)` for the popup
   monitor's DPI.
2. Use the system menu face as the primary DirectWrite family and the current
   candidate font families as ordered fallbacks for missing localized glyphs.
   Keep a separately named menu fallback so future candidate-font changes do
   not silently redefine the menu contract.
3. Convert the returned logical height into the render target's DirectWrite
   units exactly once. Do not multiply an already DPI-scaled value again.
4. Recreate text formats and remeasure all open menu levels after
   `WM_DPICHANGED` or a relevant system-font setting change.
5. Fall back to the system GDI menu font if DirectWrite or fallback creation
   fails; font failure must not prevent access to settings.

Update `CandidateWindow.cpp` to use the extracted helpers without changing its
current tint, alpha, rounded corners, transparent D2D clear, or theme refresh.

### Phase 4: Implement the Custom Popup Renderer

Add a dedicated `SettingsMenuWindow`/view implementation using the existing
`CBaseWindow` and candidate/OptionsView paint patterns where appropriate.
Register its window class through `Globals.*`, and add every new `.h`/`.cpp`
file to both `Jyutping.vcxproj` and `Jyutping.vcxproj.filters`.

Use one popup/tool window per visible menu level. Each level owns only its
layout and interaction state while the root tracking object owns the immutable
snapshot, open submenu chain, final command ID, and dismissal reason.

Rendering requirements:

- transparent D2D clear over successful acrylic composition, otherwise a fully
  opaque themed background;
- candidate-window normal, highlight, and border colors in ordinary light/dark
  mode, with contrast-checked selected and disabled text;
- radio indicators, submenu arrows, separators, disabled text, hover state,
  and keyboard focus indication;
- row height, gutters, arrow space, padding, and popup width derived from
  measured text plus DPI-scaled system menu metrics;
- no wrapping or clipping of localized labels at supported DPIs;
- D2D/DirectWrite as the primary path and a complete GDI opaque fallback; and
- small rounded corners on supported Windows 11 builds, with a conventional
  border on older systems.

Do not reuse `COptionsView` directly. It assumes a flat ten-row candidate UI,
candidate font settings, number shortcuts, and candidate selection semantics.
Share or extract narrow measurement/paint helpers only when doing so removes
real duplication without coupling the two views.

### Phase 5: Implement Menu Tracking and Placement

Preserve native-menu interaction closely:

1. Start the root at `PopupPointFromClick` and clamp every popup level to the
   monitor work area.
2. Cascade toward the side with available space and keep the submenu aligned
   with its parent row; handle negative monitor coordinates and mixed-DPI
   monitor boundaries.
3. Use non-document popup/tool-window styles and avoid activating the client
   document merely to display the menu.
4. Track hover with `TrackMouseEvent`; open submenus after a short system-like
   delay and close only the invalid branch of the submenu chain.
5. Support left-click selection, right-button invocation parity, mouse wheel
   neutrality, pointer input, and safe capture release.
6. Support Up/Down, Left/Right, Home/End, Enter, Space, and Escape. Skip
   separators and disabled items. Numeric labels inside font/page-size
   submenus remain ordinary command text, not new global shortcuts.
7. Dismiss the complete tree on command, Escape, outside input, owner
   destruction, thread deactivation, or fatal rendering failure.
8. Preserve and verify the foreground window, focused HWND, and TSF document
   context across every exit path. Do not call `SetForegroundWindow` unless a
   proven tracking requirement demands it; if it is required, restore prior
   state deterministically.
9. Route a selected command ID to `OnMenuSelect` only after the popup tree has
   released capture and closed, preventing setting-driven UI refresh from
   re-entering a live menu window.

Keep popup tracking on the creating UI thread. Do not add worker threads or a
second process for menu presentation.

### Phase 6: Add Accessibility and System-State Updates

Expose the root and submenu levels as menus and each visible row as a menu item.
The provider must report:

- localized name and command identity;
- enabled/disabled, selected/focused, checked, and expanded/collapsed state;
- parent/child/sibling navigation and screen bounds; and
- invoke and expand/collapse actions that enter the same internal paths as
  mouse and keyboard input.

Raise accessibility events when focus, hover/selection, checked state, submenu
visibility, or popup visibility changes. `WM_GETOBJECT` must not return a
provider after the corresponding menu level is destroyed.

Handle these system changes while a popup is open:

- `WM_SETTINGCHANGE`: theme, high contrast, transparency, menu font, and text
  metrics;
- `WM_THEMECHANGED`: themed colors and opaque fallback resources;
- `WM_DWMCOLORIZATIONCOLORCHANGED`: accent/highlight resources; and
- `WM_DPICHANGED`: suggested bounds, text formats, measurements, and the open
  submenu chain.

Repaint or re-layout in place where safe. If a structural refresh cannot be
performed safely during tracking, dismiss cleanly and let the next right-click
rebuild a fresh snapshot.

### Phase 7: Integrate with the Language-Bar Button

Update `ShowSettingsMenu` to:

1. build one snapshot;
2. attempt to initialize and track the custom popup;
3. call `OnMenuSelect` for a returned command; and
4. return a failure or cancellation result cleanly if popup initialization or
   tracking fails, leaving the next right-click free to retry.

Keep `OnClick(TF_LBI_CLK_RIGHT, ...)` on this direct path and keep
`InitMenu` model-driven for TSF compatibility. After the custom path is
runtime-verified, delete the direct `CreatePopupMenu`, `AppendMenuW`,
`CheckMenuRadioItem`, `TrackPopupMenu`, and `DestroyMenu` construction helpers.
Do not retain an `HMENU` popup fallback.

Audit all allocations and teardown paths for popup levels, D2D resources,
DirectWrite formats, accessibility providers, timers, capture, and registered
window classes. Destruction must not outlive or release
`ILangBarItemButtonSettingsMenuHandler`.

### Manual Runtime Matrix

Appearance and system state:

- light theme, dark theme, and high contrast;
- transparency effects enabled and disabled;
- DWM composition success and forced opaque fallback;
- Windows accent-color changes while open and between openings;
- menu-font/text-scale changes; and
- Windows 10 conventional border and Windows 11 rounded-corner behavior.

Layout and localization:

- all six resource locales;
- 100%, 150%, and 200% DPI;
- mixed-DPI multi-monitor moves and negative monitor coordinates;
- root and every submenu opened near all work-area edges; and
- missing preferred fonts, CJK labels, Latin text, numbers, punctuation, and
  check/arrow glyph fallback.

Interaction and lifecycle:

- mouse hover delays, submenu switching, command clicks, and disabled rows;
- complete keyboard navigation and Escape cancellation;
- outside-click/light dismissal, owner destruction, theme/DPI change, and DLL
  teardown while open;
- repeated rapid open/close cycles with no leaked HWND, capture, timer, GDI,
  D2D, DirectWrite, or COM objects; and
- Narrator and Accessibility Insights navigation, state announcements,
  invocation, submenu expansion, and focus order.

Behavioral regression:

- every existing command persists the same value and refreshes visible
  candidates exactly as before;
- the exact top-level order, localized labels, checked values, and disabled
  version/footer remain unchanged;
- left-click still toggles Cantonese/ABC, while right-click never toggles it;
- focus returns to the same client control and typing continues immediately;
- forced custom initialization failure leaves no orphaned HWND, capture, timer,
  foreground-window change, or persistent failure on the next right-click; and
- candidate-window and `COptionsView` appearance, sizing, and shortcuts remain
  unchanged after helper extraction.

## Risks and Mitigations

- `SetWindowCompositionAttribute` is undocumented. Keep dynamic lookup,
  isolate it behind a failure-returning helper, and always provide an opaque
  themed path.
- Custom menus can regress input, focus, and dismissal. Keep one root tracking
  owner, fail cleanly during initialization, and make focus/capture checks a
  release gate.
- Custom rendering removes native accessibility for free. Implement and test
  the accessibility provider before enabling the custom path by default.
- Shared helper extraction can alter the candidate window. Keep extraction
  mechanical, compare baseline screenshots, and land it separately from new
  popup rendering.
- The IME runs inside arbitrary client processes. Avoid global hooks, global
  theme changes, shell-window subclassing, background threads, and assumptions
  about the host's top-level window class.
- `ITfMenu` appearance is host-controlled. Require semantic parity only and do
  not block completion on visual parity for that compatibility path.

## Definition of Done

This roadmap is complete only when the installed IME's direct right-click menu
uses the custom CandidateWindow-style presentation in ordinary operation,
contains no direct native `HMENU` fallback, preserves the complete existing
settings contract, passes the `Debug|ARM64` build, and has been manually
verified for theme, high contrast, DPI, localization, multi-monitor placement,
mouse, keyboard, dismissal, focus, accessibility, persistence, and
candidate-window regressions.
